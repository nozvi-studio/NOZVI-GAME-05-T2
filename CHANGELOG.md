### Fixed

- Office details (review follow-ups 2026-11-20): the desk mouse and books keep their proportions inside their layout box (uniform `contain` fit) instead of being stretched; the office sign sits in the wall above the main door (layout y 2.6) instead of over the door leaf, so the door swing no longer passes through it.
- Remote avatars jumping on slow frames (T-1377): patches handled in one burst keep 50 ms spacing, and the interpolation delay grows with the frame time (100 ms floor, 400 ms cap), so a remote avatar no longer holds and then jumps 0.7 m; `remote.spec.ts` walk test 20/20 in ten repeats (was the CI e2e blocker of the deploy workflow).
- High render quality frame rate (owner: below 30 FPS on every machine, 2026-11-20): bloom is off, so frames render directly instead of through the MSAA + bloom composer; the sun shadow map only holds static casters and is redrawn every 0.5 s or while a door swings, not every frame (the local avatar has a blob shadow like remote avatars); the pixel ratio is capped at 1.5; a frame-rate governor lowers the pixel ratio to 1 and then turns shadows off when a machine stays below 45 FPS. SwiftShader, ten employees: DPR 2 2567 -> 358 ms per frame, DPR 1 687 -> 415 ms. Unit `test/adaptiveQuality.test.ts`.
- Decor placement (T-1158 review): the pantry coffee machine and upper cabinets take their boxes from the layout components (`at` in `office-decor.json`) instead of copies, so the drawn machine moves with the interaction point.
- PMREM environment (T-1149 review): the whole render target is disposed, not only its texture.
- Room shell details (T-1151, review 2026-11-20): the room-wide merged skirting, wainscot, chair rail, accent wall, window frames, glass, ceiling seams and sign were camera occluders, so when the camera clamped behind one wall the detail of every wall blinked out. They are no longer occluders (the walls already occlude); the two door headers stay occluders, one mesh per door (+1 draw call). Unit test in `test/roomDetails.test.ts`.
- TV catalog videos failing with "This video can't be played here" (IFrame error 5) and the TV picture not filling the TV (owner screenshot `PRD/error.png`, 2026-11-20). Found by running the game in real Chrome on the owner's machine with `window.__tvLog`: (1) cueing the next video makes the IFrame player report `paused` for the previous one before the new one is cued, and the adapter took that as the new video's start, so held seeks and rates reached the iframe while the new video was still loading; the adapter now counts a start only after the loaded video is cued. (2) YouTube lists only 0.25 rate steps, so every 0.95 / 1.05 nudge became the T-1374 seek fallback, and each seek buffered for 0.6-1.3 s and caused the next one (a seek almost every second); the fallback now seeks only beyond `BALANCE.tv.driftTargetSeconds` (1.0 s), drift above 2 s is still a hard seek. (3) The layout `tv_screen` was 1.4 x 0.8 m on a 2.1 x 0.9 m `televisionModern` model whose display face spans about 2.05 x 0.73 m, so the model's light metal face showed beside the picture; it is now 2.04 x 0.72 m centred on the display face (y 1.568). Real Chrome after the fix: three catalog videos in a row play with one catch-up seek each and no error. Unit tests in `test/tv/player.test.ts`, `test/tv/tvBinding.test.ts`, `test/tv/tvScreen.test.ts`.
