## 2026-11-13 — Client prediction: rate cap, local seating and dev teleport (T-1037)

Context: The local player is now driven by fixed-step prediction (`apps/web/src/net/prediction.ts`) reconciled against the server's `x, z, heading, lastSeq`. The server has no teleport and does not own seats until T-1036 / T-1039.
Choice: Steps follow the frame clock (backlog capped at three steps) and a sliding window defers any step that would make more than `BALANCE.net.tickHz` inputs in one second, so frames that batch two steps never exceed 20 per second. Replays within `BALANCE.net.reconcileEpsilon` (1 mm) change nothing; larger corrections are blended over `BALANCE.net.correctionBlendSeconds` (0.15 s). The DEV `teleport` / `setPose` hook detaches prediction from server patches for the rest of the session (inputs are still sent), so e2e poses keep working without a server change. Sitting stays local; standing re-bases the prediction at the stand point and the next patch blends it back to the server position.
Alternatives: A dev-only server teleport message (needs a server change, out of scope for T-1037); snapping corrections (visible pops); ignoring the rate cap edge case (21 inputs in a one-second window when frames batch steps).
Consequence: After a dev teleport the local client no longer matches the server (remote viewers see the server position). Until T-1039 sends sit intents, the server never seats the local player, so standing up slides the avatar back to where E was pressed. The T-1036 server stands a seated player at the seat's interaction point before applying a moving input; the client's re-base at the stand point mirrors that, so once T-1039 lands the stand should need no correction (to be verified there).

## 2026-11-13 — Reconnect: own retry path only, Rejoin resumes first (T-1051)

Context: REQ-NET-005 / REQ-NET-006 need a 20 s reservation, 1/2/4/8 s backoff and an explicit Rejoin; the PoC showed the SDK's auto-reconnect refuses in the first 5 s of uptime. @colyseus/core 0.18 calls `onDrop` for any close other than a consented leave and `onLeave` after a reservation expires.
Choice: The client switches the SDK's auto-reconnect off (`room.reconnection.enabled = false`) and runs only its own `ReconnectMachine` (one reconnect attempt after each backoff delay, 4 s attempt timeout, never past the 20 s window, a server refusal ends the backoff at once). The token is stored in `sessionStorage`; without storage a drop goes straight to Rejoin. Rejoin first tries to resume with the token (in-memory copy if storage failed) and only joins afresh when the server no longer holds the session, so one person never has two employees. A resumed session is a new room handle with the same `sessionId`: `Game.attachRoom` rebinds instead of rebuilding the scene, and the predictor drops pending inputs and snaps to the server position (the server discards queued inputs and intents on a drop so the held avatar stands still; seqs keep counting up). Closing a tab is a drop, so e2e uses the door exit for consented leaves. The server's window is `roomServices.reconnectSeconds` so tests can shorten it; the shipped value is the balance value.
Alternatives: Both the SDK and our own retries (two paths racing for the same token); a fresh join on Rejoin always (duplicate employee while the old one is held); a consented leave on `pagehide` (would also end the reservation on a reload).
Consequence: Reloading the page does not resume the session yet (the token is stored but the join screen does not read it); that, and server cold-start messaging, are left for Phase 5. Inputs typed while disconnected move the local avatar until the resume snaps it back.

## 2026-11-13 — Network test profile is our own outgoing delay line (T-1041)

Context: REQ-NET-004 asks for a manual 10-minute run at 100 ms RTT and 1% loss. WebSocket runs on TCP, so a lost segment is resent and holds back everything behind it; the client sees a delay spike, never a missing patch. @colyseus/core 0.18.28 offers `applySimulatedLatency` / `COLYSEUS_LATENCY`, which adds one fixed delay split across both directions, with no jitter or loss model.
Choice: `apps/server/src/netProfile.ts` wraps `WebSocketClient.prototype.raw` with one in-order delay line per socket: each message waits `rttMs` ± `jitterMs`, and `lossPercent` of messages add `retransmitMs` (head-of-line blocking included). Values live in `BALANCE.net.testProfile` (100 ms, ±20 ms, 1%, 200 ms, 10 min run). Only the downlink is delayed, by the whole round trip, which gives the same input-to-acknowledgement time. On only with `NET_PROFILE=test`, never with `NODE_ENV=production`. The soak is `apps/web/e2e/netProfile.spec.ts`, skipped unless `NET_PROFILE=test`; bots for manual runs are `pnpm --filter @office/server bots`.
Alternatives: `COLYSEUS_LATENCY` (fixed delay only; it also patches the same prototype, so the two must not be combined); OS-level `tc netem` (needs root and real packet loss tooling, not portable to the owner's machine); dropping messages (not what TCP does).
Consequence: The profile approximates the network seen by one client, not real packet loss. Remote smoothness under it is measured by counting per-frame jumps in the browser; the result is in `docs/plans/phase-3.md` §10.

## 2026-11-17 — TV clock offset is sampled only from fresh `updatedAt` after the first real snapshot (T-1143)

Context: Colyseus resolves a join before the first full state arrives. `TvBinding` took the empty schema defaults as the first snapshot, so the real state's old `updatedAt` became a clock sample and a late joiner's offset lagged the server by the age of the last command (fixed in 0c3fe1a).
Choice: The binding ignores room state until it contains the session's own employee; that state is the first snapshot and is never a sample. Each later change of `updatedAt` gives one sample (`updatedAt` minus local receive time); `ClockOffsetEstimator` keeps the largest recent sample (a lower bound of the true offset, the least-delayed patch wins). Until a sample exists the local clock stands in for server time.
Alternatives: A ping/pong time sync message (wire change, more traffic); sampling every patch (most patches do not touch `tv` and carry no fresh stamp).
Consequence: A client's error is roughly its patch delay at the last command, held while under the 0.5 s ignore band (soak: at most 0.32 s against server time, 0.21 s between clients). A same-handle SDK reconnect can give one late sample; the next command corrects it. Update 2026-11-19 (T-1567): a late joiner no longer waits for the next command; it takes `tv_time` samples on join (entry below).

## 2026-11-19 — TV clock sample on join: `tv_time` request and reply, `PROTOCOL_VERSION` 7 (T-1567, OQ-023)

Context: The Phase 4 review found that a late joiner kept offset 0 until the next TV command, because the join snapshot's `updatedAt` is never a sample (entry above). With two machines whose clocks differ, its `expectedTime` was off by the whole skew (for example 1.5 s), and the drift sync could not see it because it reads the same skewed clock. e2e and the soak share one machine clock, so they cannot catch it.
Choice: New client message `tv_time` `{ id }` (uint32, validated by `parseTvTimeRequest`; extra fields dropped) answered by server message `tv_time` `{ id, serverNow }` (server epoch ms when the reply is sent; the client checks it with `parseTvTimeReply` and only accepts the id it is waiting for). `TvBinding.attach` (join and reconnect) takes `BALANCE.tv.clockSamplesOnJoin` = 3 samples, one request at a time. Each reply gives the same lower-bound sample as a fresh `updatedAt` (`serverNow` minus local receive time) to `ClockOffsetEstimator`, which keeps the largest; the rule that a join snapshot's stale `updatedAt` is never a sample stays. If a sample moves a playing TV's expected position by the ignore band (0.5 s) or more, the binding seeks to it as a late-join command would (before the video starts the player only moves its start position, T-1405); a paused TV does not depend on the clock. The server answers behind its own per-client `CommandRateLimiter` (`BALANCE.tv.timeRequestsPerWindow` = 6 per `rateLimitWindowSeconds` = 10 s), so clock samples never use up the 5 TV commands; invalid or over-budget requests are dropped without a reply or `tv_rate_limited` notice (a notice would hold the client's TV commands). `PROTOCOL_VERSION` 6 -> 7: an @colyseus/core 0.18 server outside dev mode disconnects a client that sends a message type it has no handler for, so a new client must not reach an old server (same rule as plan 4.1 §8: one version step per protocol task). TvSim and the drift bands are unchanged.
Skew limit: none on the size of the skew; any constant offset is learned on join. The residual error is the shortest server-to-client delay among the samples (at most one round trip; the unit test shows 30 ms against a 1.5 s skew), and it must stay under the 0.5 s ignore band to be invisible and under the 1.0 s drift target. Clock drift during a session (NTP steps, sleep) is still corrected only by later `updatedAt` samples; because the estimator keeps the largest of its last 20 samples, a local clock stepped forward is not learned until older samples age out.
Alternatives: Midpoint (NTP-style) estimate `serverNow - (sent + received) / 2` (tighter on symmetric links but no longer a lower bound, so it does not mix with the `updatedAt` samples); Colyseus `room.request` (newer API, no existing pattern in the repo); sending the server time in the join reply or a state field (a stale value by the time it is decoded, and a schema change); reusing the TV command budget (a reconnect burst could block TV commands).
Consequence: A late joiner on a skewed machine shows the right position before any command (unit `tvBinding.test.ts` "a late joiner with a local clock ±1500 ms off the server learns the offset on join"). Real two-machine skew is still not covered by e2e; the Phase 5 deployment check should include one playtest across two machines.

## 2026-11-17 — TV errors stay local; e2e uses a fake player (T-1140, T-1144)

Context: A video can fail on one client and play on another (embedding, region, codecs), and the YouTube iframe cannot run in headless e2e.
Choice: An IFrame `onError` (2, 5, 100, 101, 150) marks the video failed for that client only: the player stops, the screen and panel show a per-video message, the catalog item is disabled, and the shared state is left alone. ## 2026-11-20 — High-quality FPS pass: no bloom, static shadow map, pixel-ratio cap, frame-rate governor

Context: Owner report 2026-11-20: in `high` render quality every machine fell below 30 FPS (Phase 3 read about 55). Since then Phase 4.1 added an `EffectComposer` (4x MSAA half-float targets, bloom, output pass), a PMREM environment, softer PCF shadows and more casters, at a device pixel ratio up to 2. Measured in a Claude Code cloud container (headless Chromium, SwiftShader, 1280x720, ten employees: one browser plus nine walking bots, spawn view; absolute numbers are CPU rendering, only the ratios matter): DPR 1 687 ms per frame; bloom and composer off 426; plus static shadow map 415; DPR 2 2567 ms before, 781 after the cap with no step down, 358 after the governor stepped to DPR 1 without shadows. Ablations at DPR 1: shadows off 354, PMREM off 310.
Choice: (1) Bloom strength 0 (the plan §6.5 gate: drop bloom if it costs more than 5 FPS); with bloom off `postProcessingConfig` returns null, so `high` renders directly with the canvas's own antialias instead of the composer. (2) Only static meshes cast sun shadows: the local avatar gets the same blob shadow as remote avatars, `renderer.shadowMap.autoUpdate` is off, and `ShadowRefresh` (`lighting.ts`) redraws the map on the first frame, every `BALANCE.rendering.shadow.refreshSeconds` (0.5 s, for furniture that loads later) and on every frame while a cabinet, fridge or door leaf swings. Alternatives: Keep bloom at a lower resolution (still two half-float targets and a mip chain for a mild glow); drop PMREM (biggest remaining ablation, but it gives the reflections T-1149 asked for; the governor can be extended to it if the owner's numbers need it); a quality menu (UI work and a choice most users never make); stepping quality back up (oscillation between steps).
Consequence: Strong machines keep reflections, static soft shadows and a sharper image; weak ones settle at DPR 1 without shadows within about 10 s. No avatar casts a sun shadow any more. The composer code stays and returns if bloom strength is raised. The owner's real-hardware FPS reading is still the acceptance evidence (T-1150, T-1160).
